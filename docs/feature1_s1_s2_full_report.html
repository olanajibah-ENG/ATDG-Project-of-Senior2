1. الفكرة باختصار

المستخدم بيطلب اختبارات لمشروعه (أو لملفات منه). النظام ما بيبعت كود الملفات بالطلب: بيعتمد على التحليل المخزّن أصلاً لكل ملف (AST، الكلاسات والميثودات، والـ graph)، وبيبني خطة بالوحدات (ميثود أو دالة)، وبيكتب لكل وحدة اختبار pytest بنموذج لغوي، وبيفحصه بدون ما يشغّله. التشغيل الحقيقي بالـ sandbox هو الشريحة الجاية (S3).

الشريحةشو بتعملالحالة
S1مهمة (job) + بوابة التحليل + graph المشروع + الخطة. بدون نموذج لغوي.خالصة
S2توليد اختبار unit لكل وحدة، وفحصه بدون تشغيل. الحالة generated.خالصة
S3تشغيل الاختبارات بـ sandbox. الحالة ready بس من بوابة القبول.الجاية

مكان الكود: كل الميزة جوّا Ai_project/core_ai/services/test_generation/، متل باقي الميزات. الـ views والـ serializers والـ models ومهمة Celery بأماكنها المشتركة بـ core_ai. الروابط تحت /api/analysis/tests/jobs/. وفي اختبار (test_boundaries.py) بيتأكد إنو الميزة ما بتستورد النموذج إلا من باب واحد (llm_facade.py)، وما بتستورد من ميزة تانية.

2. S1: المهمة والبوابة والـ graph والخطة

2.1 كيف بتمشي المهمة

POST /api/analysis/tests/jobs/  {project_id, version_number?, paths?, levels?}
   └─► 202 {job_id, status: pending}
        Celery: core_ai.testgen.advance_job
          queued ─► waiting_analysis ─► planning ─► planned ─► (S2) generating ─► generated
  1. التحقق والنطاق (scope.py): النسخة (الأحدث إذا ما انحددت)، الملفات، والمستويات unit / edge / integration. محتوى الملفات ما بينبعت أبداً (snapshot ← 400).
  2. ملكية المشروع (project_access.py، انضاف بعد S1): UPM بيقرر بتوكن المستخدم. مشروع مش إلك ← 404.
  3. بوابة التحليل (gate.py): لكل ملف قرار: محلّل، بانتظار التحليل (بيطلبه)، فشل مرتين، أو مش Python ← متروك مع السبب.
  4. الـ graph (graphify/): دمج graphs الملفات المخزّنة بمعرّفات فريدة path::Class.method وربط الاستدعاءات (القسم 4).
  5. الخطة (planner.py): الوحدات، والمتروك وسببه، و work_items_count = الوحدات × المستويات. وكل وحدة معها callees (يلي بتناديهم جوّا المشروع) و externals.

2.2 الأمان والأخطاء

  • كل رابط بيطلب توكن UPM (auth.py): بيتحقق من التوقيع والانتهاء ونوع access. والـ job ما بيقراه غير صاحبه (403).
  • شكل موحّد لكل خطأ: {"error": {"code", "message", "details"}}. الأكواد: 400، 401، 403، 404، 409 (الخطة لسا ما جهزت)، 422 (ما في ملف Python)، 503 (UPM ما جاوب).
  • إصلاح المهمة العالقة (staleness.py): job ما شغّله العامل أكتر من المهلة بيتحوّل failed مع السبب، بدل ما يضل pending للأبد.

3. S2: توليد اختبار unit بدون تشغيل

3.1 الخطوات لكل وحدة

  1. الـ context (context.py): جسم الوحدة، توقيعها مع القيم الافتراضية، الكلاس حواليها (الباني والخصائص)، توقيعات الوحدات يلي بتناديها (مش أجسامها)، والأسماء الخارجية. ما في ملف كامل، وما في جسم وحدة تانية.
  2. طلب واحد للنموذج لكل وحدة (generation.py، llm_facade.py): وحدة وحدة بكل جولة، وكل طلب بينسجّل (النموذج، الرموز، المدة) بـ test_attempts. حد أعلى: 20 طلب لكل job.
  3. إعادة الاستعمال: إذا نفس الـ context ونفس نسخة التوجيه انطلبوا قبل، بيرجع الجواب المحفوظ بدون طلب جديد.
  4. الفحص بدون تشغيل (validation/): استخراج الكود، جواب مقطوع؟، تحليل AST، الاستيرادات المسموحة، قوة الاختبار (في assert؟)، أسماء الاختبارات، وقواعد أمان (ما في شبكة ولا عمليات ولا eval ولا نوم ولا كتابة برّا tmp_path).
  5. الحفظ (records.py): record لكل وحدة × مستوى بـ test_records. النجاح ← generated مع مسار الملف ورأسه (assembler.py). الفشل ← generation_failed مع السبب. ready ممنوع هون.

8. شو ضل، وحدود معروفة

  • S3: تشغيل الاختبارات بـ sandbox، وبوابة القبول يلي بس هي بتعطي ready.
  • الفرونت: بعد رفع zip ما بيقرا حالة المهمة (فالرفض بيبيّن انتهاء وقت)، وما فيه "أكّد الحذف" ولا اختيار مجلد. منقارن مع الفرونت الأخير ومنكتب ملاحظة لأريج.
  • روابط التحليل (analysis-results، project-tree، ...) AllowAny بدون توكن: بدها قرار وتنسيق مع الفريق.
  • حد OpenRouter المجاني: 50 طلب باليوم لكل النماذج مع بعض. و laguna-s (نموذج التقييم) ما عاد موجود.
  • graph الشرح ما بيستفيد من ربط الاختبارات لسا. ورابط graph كامل للمشروع (البند 2) مأجّل.
  • كل إعادة تحليل بتزيد سجل (ما بينمسح القديم). الرابط بيرجّع الأحدث، بس السجلات بتكبر.
  • بعد restart ai_web لازم restart upm_api_gateway، وإلا 502.
